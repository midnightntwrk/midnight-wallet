## High-level summary

The 2.x line adds hard-fork support: the wallets run ledger-v8 below the chain's `forks.v9` and ledger-v9 from it, and
follow a live chain across that boundary with balances, coins and transaction history carried over (release body). The
public API is reworked around it: wallets start from seeds or from each ledger version's keys, transactions travel as
`WalletTransaction` handles stamped with the protocol version that built them, signers are asynchronous, and one
lifecycle record follows each transaction (release body). The Breaking changes section below lists what integrators must
change, and the facade release notes carry the migration guide (release body).

## Audience

This release is for:

- **External integrators** who build wallets on Midnight, move tokens from their DApps, manage shielded, unshielded and
  Dust balances, or run atomic swaps.
- **Shielded Technologies** engineering teams who maintain the SDK, its test harness or services built on it.
- Teams whose applications must keep working while the chain they target crosses the ledger-v9 fork.

## What changed

- The wallets follow a live chain across the ledger-v9 fork, carrying balances, coins and transaction history over.
  (release body)
- Wallets and the facade start from seeds or from each ledger version's keys, and no transacting method takes secret
  keys. (release body)
- Transactions are `WalletTransaction` handles that carry the protocol version they were built for. (release body)
- Signers are asynchronous, and keys and signatures are tagged `{ tag, value }` objects. (release body)
- One lifecycle record per transaction replaces the pending-transactions service. (release body)
- Sync completion also waits for the indexer's reported tip to be checked against a node's finalized head. (release
  body)
- The unshielded wallet supports ECDSA keys on ledger-v9, beside schnorr. (CHANGELOG)
- The facade validates a transaction against real ledger parameters before it is submitted. (CHANGELOG)
- The Dust wallet can sync from the indexer's projections instead of replaying every Dust event. (CHANGELOG)
- Coins booked for transactions that are abandoned, never included or only partly successful are released, and a resync
  no longer doubles the unshielded balance. (CHANGELOG)
- Paying a fee with Dust dates the spend only at a block whose Dust tree roots the wallet holds: balancing waits for the
  wallet's sync, up to two minutes, and otherwise fails with `SyncWalletError`. (CHANGELOG)
- `MidnightBech32m.parse` accepts addresses longer than 90 characters, so shielded addresses parse with `@scure/base`
  2.4.0, and it checks the payload size of shielded addresses and shielded encryption public keys. (CHANGELOG)
- Indexer subscriptions are compressed when the indexer offers it. (CHANGELOG)
- The prover client checks the key material it downloads against the hashes its ledger release declares. (CHANGELOG)
- The test harness can run every scenario on either Dust sync model, and its state waiters wait for what they name.
  (CHANGELOG)

## New features

### Following the chain across the v9 fork

**Description**: The shielded, unshielded and Dust wallets each run a ledger-v8 variant below `forks.v9` and a ledger-v9
variant from it, and hand over when the chain crosses. Shielded coins cross at their positions in the commitment tree,
every unshielded UTxO is carried, and the Dust state is rebuilt from the chain. A transaction still pending at the
crossing can never be included: it is recorded as orphaned and its coins are released. A shielded or Dust wallet with no
traffic of its own still notices the fork, because its sync asks for the chain tip every 30 seconds; the unshielded
wallet reads the protocol version from the indexer's progress messages. A wallet restored from a snapshot crosses too.
(CHANGELOG)

### `WalletSeeds.fromMasterSeed`

**Description**: Derives the shielded, Dust and unshielded seeds a wallet starts from, by default for account 0, address
index 0 and the `Roles.NightExternal` role, and wipes the BIP32 root afterwards. It throws `SeedDerivationError` for a
seed it cannot read or an account or index out of range. (CHANGELOG)

### ECDSA unshielded keys

**Description**: On ledger-v9, an unshielded wallet can hold an ECDSA key beside schnorr, derived under its own role,
`Roles.EcdsaUnshielded`, so its secret is never shared with the schnorr roles of the same account. A wallet's signature
scheme is enforced: a signature in the other scheme is refused before it is attached, so no partly signed transaction
reaches the network. (CHANGELOG)

### `validateTransaction`

**Description**: `facade.validateTransaction(tx, { flags, blockData? })` checks that a transaction is well formed before
it is submitted, against real ledger parameters, at the protocol version its handle carries. Recipes from the balancing
methods carry the block data they were priced with, so balancing, validating and submitting fetch no block twice.
Failures are tagged errors: `WellFormedError` and `ValidationFetchError`. (CHANGELOG)

### `adoptTransaction`

**Description**: `facade.adoptTransaction(bytes, stage)` reads a transaction from bytes that name no protocol version,
such as those the DApp Connector API passes, at the version the facade is acting at, and returns the sealed handle.
Bytes written by the other ledger version are refused with a `WireFormatError` that names the version. (CHANGELOG)

### Protocol position in facade state

**Description**: `FacadeState.protocolVersion`, `activeProtocolVersion` and `protocol` report where the wallets are:
`Settled` at a version, or `Crossing` from one version to the next. (CHANGELOG)

### Dust fee coverage estimate

**Description**: A first-time Dust registration whose generated Dust cannot yet pay its own fee rejects with
`InsufficientDustForFeeError`, which carries the fee, the shortfall, the claimable amount and an estimate of when
generation will cover it. One class serves both ledger versions, so `instanceof` recognises it. (CHANGELOG)

### Reserved coins and booking lifetimes

**Description**: `ShieldedWalletState.reservedCoins` lists the coins booked for a transaction that has not settled, with
when each was booked and when it can be released. The shielded builders take an optional trailing `ttl` that caps how
long the coins they book stay booked, and the unshielded wallet adds `revertUtxos` to release booked coins by id.
(CHANGELOG)

### Snapshot inspection and forward-compatible saves

**Description**: Each wallet's `tryRestore` returns an `Either` instead of throwing. The shielded `Restore` and
unshielded `UnshieldedRestore` namespaces inspect a snapshot's protocol version and writer before restoring, and the
Dust wallet's `peekProtocolVersion` reads a snapshot's protocol version. Snapshot and history fields this build does not
declare are kept and written back, so a field written by a later release survives a rollback. (CHANGELOG)

### Ledger and variant subpaths

**Description**: `./ledger/v8` and `./ledger/v9` re-export each ledger version for applications that build their own
transactions, and `./shielded/v2`, `./dust/v2` and `./unshielded/v2` export the ledger-v9 variants beside the `/v1`
ones. The root exports `Signing`, `Token.night`, `parseTokenType`, `DustGenerationRates` and the Dust parameter
converters, so token types, signatures and Dust parameters need no ledger import. (CHANGELOG)

### Bridge claim transactions

**Description**: The unshielded wallet syncs `BridgeClaimTransaction`, as an implicitly successful transaction.
(CHANGELOG)

### Fork simulation

**Description**: `ForkSimulator` drives one simulated chain across a protocol boundary, and the ledger-v8 and ledger-v9
simulators can schedule protocol versions, so fork crossings can be tested without a live chain. (CHANGELOG)

### Test harness Dust sync selection

**Description**: In the test harness, `DUST_SYNC` selects the Dust sync model for a whole run, `events` or
`projections`, and rejects an unrecognised value. `provideWallet` reports whether the wallet came from a snapshot, and
`waitForStableState` resolves once a predicate has held for a settling window. (CHANGELOG)

## New features requiring configuration updates

### Dust projections sync

**Required updates**: (CHANGELOG)

- Compose `CustomForkingDustWallet` with the `./v2` `SyncService.makeEventLessSyncService` as its ledger-v9 sync and an
  event-replaying ledger-v8 variant. (CHANGELOG)
- Optionally set `backgroundSyncInterval`, five seconds by default. (CHANGELOG)

**Impact**: The Dust wallet syncs from the indexer's projections in finite passes instead of replaying every Dust event.
It needs ledger-v9 and does not hand over across a fork by itself, which is why it is composed with a ledger-v8 variant.
A restored projections wallet resumes from the block its last pass reached, and a wallet that replays events refuses a
projections snapshot with `SnapshotSyncMismatchError`. (CHANGELOG)

### Manual Dust sync

**Required updates**: (CHANGELOG)

- Start the facade with `start(material, { manualSync: true })`. (CHANGELOG)
- Call `doSync(material)` once per sync pass. (CHANGELOG)

**Impact**: Leaves the Dust wallet to be synced by hand. It needs a Dust wallet built with the projections sync, so
below `forks.v9` `start` refuses the option before starting anything, and `doSync` rejects, with
`ManualSyncUnsupportedError`. (CHANGELOG)

### Skipping the ledger-v8 Dust history

**Required updates**: (CHANGELOG)

- Set `skipLedgerV8DustHistory`, or, for a `CustomForkingDustWallet`, `ForkingDustConfiguration.dustTimelineStartProbe`.
  (CHANGELOG)

**Impact**: A fresh wallet on a chain that already crossed `forks.v9` starts at the last Dust event below the boundary
instead of replaying the ledger-v8 Dust events. The wallet's ledger-v8 Dust transaction history will be missing. Off by
default; a restored wallet resumes from its snapshot. (CHANGELOG)

### Indexer liveness check

**Required updates**: (CHANGELOG)

- Name the node to check against with `nodeClientConnection`; otherwise `relayURL` is used. (CHANGELOG)
- Tune the check with `livenessConfiguration` and `livenessPollInterval`, 30 seconds by default. (CHANGELOG)

**Impact**: The unshielded wallet cross-checks the indexer's reported tip against the node's finalized head, and its
sync completion waits for a verdict that does not block. A wallet that names neither a node connection nor a relay URL
is not checked. (CHANGELOG)

### Key material host

**Required updates**: (CHANGELOG)

- Set `KeyMaterialConfig.source` to read the prover's key material from a host of your own, such as a mirror or a
  browser page's own origin. (CHANGELOG)

**Impact**: By default the bundled key material providers read from the ledger's public host. Every file is checked
against the SHA-256 hash its ledger release declares, wherever it is read from. (CHANGELOG)

## Improvements

### Compressed indexer subscriptions

**Description**: Subscriptions negotiate the indexer's `graphql-transport-ws+deflate` subprotocol and inflate the
compressed frames, falling back to plain `graphql-transport-ws` against an indexer that does not offer it. The
subscription socket stays open for the client's lifetime, so a subscription that pauses for backpressure resumes on the
same connection. There is nothing to configure. (CHANGELOG)

### Key material from the ledger's public host

**Description**: The prover client's default key material is read from the host the ledger's own data provider reads,
rather than a development bucket. (CHANGELOG)

### Clearer URL errors

**Description**: `HttpURL.make` and `WsURL.make` refuse a URL with the wrong scheme with a message that names it,
instead of `[object Object]`. (CHANGELOG)

## Breaking changes

### Fork schedule and proving configuration

**What changed**: The wallet packages require `forks`, the protocol version from which ledger-v9 reads the chain. The
facade presets `DefaultForkSchedule` when it is left out and hands the completed configuration to every `InitParams`
factory. Proving names a backend per ledger version with `provers: { v8?, v9 }`, or one proof server under both with
`provingServerUrl`. (CHANGELOG)

**What breaks**: Constructing `ShieldedWallet`, `UnshieldedWallet` or `DustWallet` without `forks`. `WalletFacade.init`
with neither `provers`, `provingServerUrl` nor a `provingService` factory throws. A custom `InitParams.provingService`
that proves only one ledger version. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Name the proving backends with `provers`, or keep `provingServerUrl`. (CHANGELOG)
- On a chain whose nodes do not report the 2.x fork version, set `forks`. (CHANGELOG)
- Outside a facade factory, get the completed configuration from `WalletFacade.resolveConfiguration(configuration)`.
  (CHANGELOG)

**Code example**: (commit 9f1eb58)

```ts
const configuration = {
  // ...
  forks: ProtocolVersion.V9NativeForkSchedule,
  provers: { v8: { kind: 'server', url: v8ProofServerUrl }, v9: { kind: 'wasm' } },
} satisfies DefaultConfiguration;
```

### Starting from seeds or keys

**What changed**: Wallets and the facade start from seeds or from each ledger version's keys. `facade.start` takes
`WalletSeeds` or `FacadeKeysByEpoch`. The shielded and Dust wallets' `startWithSeed` and the unshielded wallet's
`startWithPublicKey` return a `Promise`, and the shielded `startWithSecretKeys` and Dust `startWithSecretKey` are
replaced by `startWithKeys({ v8, v9 })`. The secret keys argument is gone from `transferTransaction`, `initSwap`, the
`balance*Transaction` methods and `estimateTransactionFee`. A stopped facade drops its key material. (CHANGELOG)

**What breaks**: Calls that pass secret keys to transacting methods, and `start(shieldedSecretKeys, dustSecretKey)`.
Code that uses the result of `startWithSeed` or `startWithPublicKey` without awaiting it, and calls to
`startWithSecretKeys` or `startWithSecretKey`. Transacting after `stop()` fails with `MissingStartAuxError`. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Derive the three wallet seeds once with `WalletSeeds.fromMasterSeed` and start every wallet, and the facade, from
  them. (CHANGELOG)
- Await a wallet's start, or return it from the facade's `InitParams` factory as it is. (CHANGELOG)
- Drop the secret keys from transacting calls. (CHANGELOG)

**Code example**: (CHANGELOG)

```ts
const seeds = WalletSeeds.fromMasterSeed(masterSeed);
const keystore = createKeystore({ kind: 'schnorr', secret: seeds.unshielded }, configuration.networkId);
const facade = await WalletFacade.init({
  configuration,
  shielded: (config) => ShieldedWallet(config).startWithSeed(seeds.shielded),
  unshielded: (config) => UnshieldedWallet(config).startWithPublicKey(PublicKey.fromKeyStore(keystore)),
  dust: (config) => DustWallet(config).startWithSeed(seeds.dust),
});
await facade.start(seeds); // 1.x: facade.start(shieldedSecretKeys, dustSecretKey)

const recipe = await facade.transferTransaction(outputs, { ttl }); // 1.x also took the secret keys
```

### Version-stamped transactions

**What changed**: Every method that took or returned a ledger transaction uses a `WalletTransaction` handle
(`UnprovenTx`, `UnboundTx`, `FinalizedTx`, `AnyTx`) that carries the protocol version it was built for. The methods that
build, sign, prove or submit refuse a handle for the other ledger version with `ProtocolVersionMismatchError`. Recipes
require `protocolVersion`, and `InitParams.submissionService` submits `FinalizedTx` handles. (CHANGELOG)

**What breaks**: Code that passes ledger transactions to the facade or the wallets, or reads ledger transactions from
them. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Build your own transactions with `./ledger/v8` or `./ledger/v9`, by the protocol version the wallets are acting at.
  (CHANGELOG)
- Seal them with `WalletTransaction.adopt(stage, tx, protocolVersion)`, or read bytes with `adoptTransaction`.
  (CHANGELOG)

**Code example**: (CHANGELOG)

```ts
const handle = WalletTransaction.adopt('Unproven', tx, protocolVersion);
```

### Asynchronous signers and tagged keys

**What changed**: `signRecipe`, `signUnprovenTransaction`, `signUnboundTransaction`,
`registerNightUtxosForDustGeneration` and `deregisterFromDustGeneration` take a `SignSegment`,
`(data: Uint8Array) => Promise<Signature>`, so a signer whose secret never enters the process, such as an MPC
coordinator or an HSM, can sign. `createKeystore` takes an `UnshieldedSecretKey`,
`{ kind: 'schnorr' | 'ecdsa', secret }`, instead of a bare secret key, and verifying keys and signatures are tagged
`{ tag, value }` objects rather than strings. The ledger-v8 keystore moves from the unshielded package root to `./v1`. A
signer that rejects fails with `SignError`, and unshielded signing moves off `TransactingCapability` into a per-variant
`SigningService`. (CHANGELOG)

**What breaks**: Synchronous signer callbacks, `createKeystore` calls with a bare `Uint8Array`, code that reads keys or
signatures as strings, code that expects a signer's own rejection back from the unshielded signing methods, and code
that signs through an unshielded `TransactingCapability`. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Pass an asynchronous signer; a keystore's `signDataAsync` can be passed directly. (CHANGELOG)
- Pass the key scheme to `createKeystore`. (CHANGELOG)

**Code example**: (CHANGELOG)

```ts
const keystore = createKeystore({ kind: 'schnorr', secret: seeds.unshielded }, configuration.networkId);
const signed = await facade.signRecipe(recipe, keystore.signDataAsync); // 1.x: (data) => keystore.signData(data)
```

### Transaction lifecycle replaces pending transactions

**What changed**: `facade.pendingTransactionsService` is now `facade.transactionLifecycleService`, and
`FacadeState.pending` is replaced by `FacadeState.lifecycle`: one entry per transaction, with a status of `Balanced`,
`Finalized`, `Submitted`, `Confirmed`, `PartialSuccess`, `Rejected`, `Orphaned`, `Expired` or `Reverted`. Ended entries
stay listed until their TTL passes. The barrel's `./capabilities/pendingTransactions` subpath is now
`./capabilities/transactionLifecycle`, with no alias, and on the service `addPendingTransaction(tx)` becomes
`submitted(facts)` and `clear(tx)` becomes `reverted(identifiers)`. Transaction history entries carry a `lifecycle` of
`pending`, `finalized` or `rejected`, and `TransactionHistoryCommon` and `TransactionHistoryCommonSchema` are now
`TransactionHistoryEntryCommon` and `TransactionHistoryEntryCommonSchema`. (CHANGELOG)

**What breaks**: Code that reads `state.pending` or waits for it to empty, calls to `addPendingTransaction` or `clear`,
custom pending-transaction services, custom transaction history storages and their entry schemas, and `FacadeState`
constructed by hand. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Read `state.lifecycle` and wait with `isAwaiting` rather than for an empty list. (CHANGELOG)
- Save the lifecycle store with `serializeState()` and hand it back on the next start. (CHANGELOG)
- Replace a custom history storage's `upsert` with `gotPending`, `gotFinalized` and `gotRejected`, and extend
  `TransactionHistoryEntryCommonSchema` with `extendEntrySchema`. (CHANGELOG)

**Code example**: (CHANGELOG)

```ts
await firstValueFrom(facade.state().pipe(filter((state) => !state.lifecycle.some(isAwaiting))));

const stored = await facade.transactionLifecycleService.serializeState();
await WalletFacade.init({
  // ...
  transactionLifecycleService: (config, { clock }) =>
    TransactionLifecycleServiceImpl.restore(stored, lifecycleTransactionTraits(config.forks.v9), config, clock),
});
```

### Rejections of failed builds

**What changed**: A builder (`transferTransaction`, `initSwap`, the `balance*Transaction` methods),
`finalizeTransaction` or `finalizeRecipe` that fails part-way releases what it booked and rethrows the original error.
If a release fails as well, it rejects with an `AggregateError` whose `errors[0]` is the original error. (CHANGELOG)

**What breaks**: `instanceof` checks on the rejection of these methods. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Where the rejection is an `AggregateError`, look for the original error in `errors[0]`. (CHANGELOG)

### Sync completion waits for indexer liveness

**What changed**: `FacadeState.isSynced`, `waitForSyncedState()`, `isStrictlyComplete()` and `isCompleteWithin()` also
need the unshielded wallet's first indexer-liveness verdict that does not block. `Behind`, `Unknown` and `WrongNetwork`
block; `InSync`, `Ahead`, `Unavailable` and `Skipped` do not. `SyncProgressData` gains a required `indexerLiveness`.
(CHANGELOG)

**What breaks**: Against an indexer known to be stale, `waitForSyncedState()` neither rejects nor times out. Code that
builds `SyncProgressData` itself must supply the new field. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Race `waitForSyncedState()` against your own deadline, and read `progress.indexerLiveness` to see why it waits.
  (CHANGELOG)
- Build progress with `createSyncProgress()`, which defaults the field. (CHANGELOG)

### Saved state formats

**What changed**: Wallet snapshots record the variant that wrote them, transaction histories are saved as
`{ version: 'v2', entries }`, and the transaction lifecycle store saves format `v2`. Snapshots, histories and stores
saved by the 1.x line are read and upgraded. An unreadable snapshot is refused with `SnapshotRestoreError`, and
`restore` throws that tagged error. (CHANGELOG)

**What breaks**: The 1.x line cannot open the transaction histories and lifecycle store this release saves, and a Dust
wallet saved by this release goes back to 1.x only by restoring from its seed. Code that matched `Wallet.Other` for an
unreadable snapshot. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Keep each Dust wallet's seed; restoring from it is the way back to the 1.x line. (CHANGELOG)
- Match `SnapshotRestoreError` where an unreadable snapshot is handled. (CHANGELOG)

### Sealed wallet state and wider error unions

**What changed**: The `state` of `ShieldedWalletState`, `UnshieldedWalletState` and `DustWalletState` is sealed: read it
with `coreStateOf` from `./v1` or `./v2`. The states lose `capabilities`, `services` and `mapState`, and their
constructors take `(protocolVersion, state, projections)`. The `*WalletCapabilities` and `*WalletServices` types are
removed. The `WalletError` unions gain `SnapshotRestoreError` and `OutOfOrderSyncUpdateError`, and per wallet
`SchemeMismatchError`, `InsufficientDustForFeeError` and `SnapshotSyncMismatchError`. (CHANGELOG)

**What breaks**: Code that reads wallet core state directly, constructs wallet states, or matches a `WalletError` union
exhaustively. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Read core state with `coreStateOf`, and use `fromVariant` in place of `mapState`. (CHANGELOG)
- Handle the new error tags in exhaustive matches. (CHANGELOG)

**Code example**: —

### Custom wallets, variants and services

**What changed**: `CustomShieldedWallet`, `CustomUnshieldedWallet` and `CustomDustWallet` compose one ledger-v9 variant
and cannot cross a fork; `CustomForking*Wallet` composes both. The wallet APIs require new members:
`revertFailedSegments` on shielded and unshielded, `revertUtxos` and `releaseRestoredPending` on unshielded, `stepSync`
and `ensureFeeCoverage` on Dust. A runtime `Variant` requires `protocolVersionOf(state)`, `VariantContext` requires
`activationRange`, the `Runtime` interface requires `onVariantActivation`, `BaseWalletClass` gains `variantFor` and
`startAtVariant`, and `ProtocolState` requires `variantTag`. An unshielded `SyncService` requires `livenessUpdates`, and
a Dust `SyncService` requires `backgroundRepeat`. `NodeClient.Service` requires `getFinalizedBlock()`,
`getGenesisHash()` and `getBlockHashAt(height)`, and `ProverClient.Service` requires `asV8ProvingProvider()` and
`asV9ProvingProvider()`. (CHANGELOG)

**What breaks**: Custom implementations of any of these interfaces, hand-written `Runtime` fakes and wallet classes,
`ProtocolState` values built without `variantTag`, and single-variant custom wallets that were expected to run
ledger-v8. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Implement the new members, or compose with `CustomForking*Wallet` to run both ledger versions. (CHANGELOG)

### Capabilities named by ledger version

**What changed**: The ledger-v8 proving factories are renamed with a `V8` prefix, such as `fromV8ProvingProvider` and
`makeV8ServerProvingServiceEffect`, and `UnboundTransaction` is `V8UnboundTransaction`. `makeDefaultProvingService`,
`makeServerProvingService` and `makeWasmProvingService` are removed in favour of
`makeDefaultVersionedProvingService(configuration, forks)`. The simulators are exported per ledger version, under `V8`
and `V9`, and the deprecated `getBlockEventsSince` is removed. In the barrel, `Capabilities.Simulator` is now under
`Capabilities.V8`, and the `./capabilities/simulation` subpath exports `V8`, `V9` and `ForkSimulator` in place of the
unqualified `Simulator`, `SimulatorConfig`, `immediateBlockProducer` and the other helpers. (CHANGELOG)

**What breaks**: Imports of the renamed or removed proving factories, simulators, and the unqualified `Simulator` and
its helpers. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Switch to the `V8`-prefixed names, or to `makeDefaultVersionedProvingService`, which routes each transaction to its
  ledger version's backend. (CHANGELOG)
- Replace `getBlockEventsSince` with `getBlockEventsFrom`. (CHANGELOG)

### Dust balancing result and generation rates

**What changed**: `balanceTransactions` resolves `{ transaction, blockData }`, where `blockData` holds the ledger
parameters the fee was priced with. Generation rates are plain `DustGenerationRates` rather than ledger
`DustParameters`, though either is accepted. The `./v1` subpath no longer exports the wallet API, and an ECDSA signature
is refused below `forks.v9`. (CHANGELOG)

**What breaks**: Code that treats the result of `balanceTransactions` as the transaction itself, and imports of
`DustWallet` or `DustWalletAPI` from `./v1`. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Read `transaction` from the result of `balanceTransactions`. (CHANGELOG)
- Import `DustWallet`, `CustomDustWallet`, `DustWalletAPI`, `DustWalletState` and `DefaultDustConfiguration` from the
  package root. (CHANGELOG)

### Indexer client types and indexer version

**What changed**: The generated GraphQL types are scoped to the operations the client runs, so the bare schema types,
such as `Maybe`, `Scalars`, `Block` and `TransactionResult`, are no longer exported. Transaction unions gain a
`BridgeClaimTransaction` member. The client selects fields an older indexer does not serve, and depends on `graphql`
`^17`. (CHANGELOG)

**What breaks**: Imports of the bare schema types, exhaustive matches on transaction `__typename`, and indexers that do
not serve the newer schema. (CHANGELOG)

**Required actions**: (CHANGELOG)

- Use the operation types, such as `TransactionStatusQuery`. (CHANGELOG)
- Handle `BridgeClaimTransaction` in exhaustive matches. (CHANGELOG)
- Run an indexer that serves the newer schema; the SDK is tested against `4.4.0-rc.6`. (CHANGELOG)
